### 1.3 Methodology and why

- **Warm-up, then repeated timing.** V8 compiles hot functions lazily, so the first calls are slower than the
  steady state. The 3 warm-up runs absorb that cost; the 10 timed runs measure steady-state behavior.
- **Median and IQR instead of mean and standard deviation.** Timing distributions are right-skewed (garbage
  collection pauses, scheduler noise). The median and the interquartile range (Q1 to Q3) are robust against a few
  slow outliers. The mean and standard deviation are also stored in `runtime.json`.
- **Fixed seeds.** Graphs and levels are generated from fixed seeds, so every run times the same inputs.
- **Own graph generator for runtime.** Runtime graphs come from `bench/graphs.js` (random spanning tree plus random
  extra edges), not from the level generator, so that the timings do not depend on the generator.
- **ns per element.** `median_ms / (V + E)`, converted to nanoseconds. If an algorithm is O(V + E) this value
  should be roughly constant across sizes.
- **Log-log slope.** A line is fitted to log10(median time) against log10(V + E). A slope near 1 means linear growth.
  The fit is reported for all sizes and for V >= 500 (the V = 50 point is dominated by timer resolution and call overhead).
- **Strategy metrics.**
  - *Saved population %* = saved population / total population x 100, taken from the game outcome.
  - *Mean and std* are computed over all games of that strategy in the configuration (for Random: 20 x levels games).
    `strategies.json` also stores the std of the per-level means (`std_saved_pct_level_means`).
  - *Win rate* and *Citadel survival rate* are fractions of games.
  - *Approximation ratio* (n <= 20 only) = saved population of the strategy / saved population of the brute-force
    optimum on the same level; for Random the per-level value uses the mean of its 20 playouts.
  - *Equals optimum* = fraction of levels where the strategy saves at least as much as the brute-force optimum
    (for Random: the fraction of playouts, averaged over levels).
  - *Strictly beats* = number of levels where Articulation-Aware Greedy saves strictly more population than the
    baseline (for Random: than the mean of its 20 playouts), with ties and losses reported next to it.

The Firefighter Problem is NP-hard on general graphs. No polynomial-time exact algorithm is known for it, so an
exact search must be exponential in the worst case. The brute force here searches beacon placements turn by turn
with memoisation on the node-state vector (at most 3^n distinct vectors), which is why it is only used for n <= 20.
For larger n the game relies on heuristics.

## 6. Threats to validity and limitations

- **Random graph model.** Runtime results use random sparse graphs with average degree about 6; strategy results use
  the level generator (Kruskal tree plus short edges, average degree 3.2). Real maps drawn by a player or other graph
  families (grids, scale-free graphs, trees) may behave differently.
- **One machine, one Node.js version.** Absolute times depend on this CPU, memory and Node.js build; only the growth
  trends and the relative ordering are expected to transfer.
- **JIT and garbage collection.** Warm-up reduces but does not remove JIT and GC effects, especially for small inputs
  (V = 50, a few microseconds per call, close to the timer resolution) and for the largest inputs (GC pauses).
- **Node-protection-only brute force.** The brute force and the strategies place beacons only; they never sever roads.
  The "optimum" is therefore the best result for beacon-only play, not for the full action set of the human player.
- **Small n for optimality.** Exact optima exist only for n <= 20 (main comparison at n = 15, a smaller sample at
  n = 20), so conclusions about optimality at n = 30 and 60 are extrapolations.
- **Fixed target percent.** All strategy experiments use targetPercent = 60, so win rate depends on that threshold;
  saved percent is the threshold-free metric.
- **Sample sizes.** 100 levels per configuration (20 for n = 20) and 20 playouts per level for Random give stable
  averages but wide uncertainty for rare events; standard deviations are reported next to the means.
- **Seeds are not independent samples of a population.** Seeds 5000 to 5099 are consecutive integers of a PRNG, which
  is fine for reproducibility but is not a formal random sample of all possible levels.

## 7. Reproducibility

Requirements: Node.js 20 or newer, no `npm install` needed (no dependencies).

```
npm run bench                       # full run: runtime + strategies + bruteforce, writes bench/results/
node bench/run.js --quick           # smoke test, small sizes, writes bench/results/quick/
node bench/run.js --only=runtime    # one part only: runtime | strategies | bruteforce
node bench/run.js --charts          # redraw the SVG charts from the JSON files already in bench/results/
node bench/tables.js                # regenerate bench/results/tables.md (the Markdown tables used here)
npm run serve                       # then open http://localhost:8080/bench/bench.html for the in-browser benchmark
```
